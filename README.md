# IR開示資料 レビュー・翻訳エージェント

日本語のIR開示資料を読み込み、表記・用語・数値の検査と英訳のレビューを行うエージェントです。

CLIとWeb UIの両方から使えます。LLM を使わない検査だけなら、APIキーなしで動きます。

```
$ ir-review review data/sample_disclosure_ja.md --no-translate

┏━━━━━━━━┳━━━━━━━━┳━━━━━━┳━━━━━━━━━┳────────────────────────────────────────────┓
┃ 重要度 ┃ 出所   ┃ 規則 ┃ 箇所    ┃ 内容                                       ┃
┡━━━━━━━━╇━━━━━━━━╇━━━━━━╇━━━━━━━━━╇────────────────────────────────────────────┩
│ 要修正 │ ルール │ R006 │ p1-s016 │ 断定的な表現「必ず」が使われています…      │
│ 要確認 │ ルール │ R004 │ p1-s006 │ 用語集の正式表記は「営業利益」ですが…      │
│ 要確認 │ ルール │ R002 │ p1-s012 │ 金額単位が混在しています（千円, 百万円）    │
│ 軽微   │ ルール │ R001 │ p1-s011 │ 全角数字が 3 文字含まれています（１２４）   │
└────────┴────────┴──────┴─────────┴────────────────────────────────────────────┘
```

## 設計の中心にある考え方

**LLM に任せる範囲を、意図的に狭くしています。**

開示資料のレビューでは、金額の桁違いや用語の不統一を見逃すコストが高い。これらを確率的な判定に委ねる理由はありません。機械が確実に判定できるものは、機械が判定するべきです。

そこで検査を2層に分けています。

|  | 担当 | 対象 | 性質 |
| --- | --- | --- | --- |
| 決定論的ルール | `rules.py`（LLM 不使用） | 数値の一致、用語集の適用、表記ゆれ、断定表現 | 再現性がある。同じ入力なら常に同じ指摘 |
| LLM レビュー | `llm.py` | 訳抜け、文意のズレ、トーン | 確率的。人の確認が要る |

この分離から、いくつかの設計が導かれます。

**① 指摘には必ず「出所」が付く。** レポート上でルール由来とLLM由来を区別します。前者は反証可能で、後者は人が確認すべきもの——読む人にとって意味の違う情報だからです。

**② LLM の担当範囲を、プロンプトと型の両方で縛る。** レビュープロンプトには「数値・用語集・表記ゆれは既に検査済みなので絶対に指摘するな」と明記し、さらに返せる `category` を `omission` / `meaning` / `tone` の3つに限定したスキーマで検証します。プロンプトの指示は守られないことがあるので、型でも縛ります。

**③ 用語集は「守らせる」だけでなく「守られたか検算する」。** 翻訳プロンプトに用語集を注入したうえで、訳文に指定訳語が実際に現れているかをコードで確認します。違反があれば、違反内容そのものを添えて再翻訳を依頼します。LLM の自己申告を根拠にしません。

**④ 失敗を握りつぶさない。** 翻訳やレビューが失敗したセグメントは、黙って飛ばさず「未処理です。人による確認が必要です」という要修正の指摘として残します。レビュー済みに見えて実は未レビューという状態が、開示物では最も危険だからです。

## 実装されている検査ルール

`ir-review rules` で一覧を表示できます。

| ID | 対象 | 内容 | 既定の重要度 |
| --- | --- | --- | --- |
| R001 | 原文 | 全角数字の混入 | 軽微 |
| R002 | 原文 | 金額単位の混在（百万円 / 千円 など） | 要確認 |
| R003 | 原文 | 和暦と西暦の混在 | 要確認 |
| R004 | 原文 | 用語集の正式表記に対する揺れ | 要確認 |
| R005 | 訳文 | 金額・比率の不一致（単位換算込み・過不足の両方向） | 要修正 |
| R006 | 原文 | 断定的な表現 | 将来見通しなら要修正、実績なら要確認 |
| R007 | 訳文 | 用語集の指定訳語が使われていない | 要修正 |
| R008 | 訳文 | 使用禁止の訳語が使われている | 要修正 |
| R009 | 訳文 | 日付・序数などの数値が訳文で確認できない | 要確認 |

### 誤検出をどう潰したか

ルールの質は、何を拾うかより何を拾わないかで決まります。実際に踏んだ誤検出は、対処と一緒に回帰テストへ残しています。

**数値照合を、リスクの質で二分した（R005 / R009）**

「2026年3月期 第2四半期決算に関するお知らせ」というタイトル行で、`3`（March）と `2`（Second）が訳文に無い、という誤検出が出ました。英語では日付や序数が語になるためです。

ここでチェックを緩めるのは誤りです。金額の桁違いこそ、このシステムが最も拾うべきものだからです。そこで数値を2種類に分けました。

- 金額・比率（単位・パーセント・小数点・桁区切りを伴う）→ 厳密に照合し、要修正
- 裸の整数（日付・四半期番号など）→ 英語の語（`March` / `Second` / `ten`）も数値として認識したうえで、原文にあって訳文のどこにも見当たらないものだけを要確認

`ten locations` は許容し、`several locations` は指摘する、という区別まで含めてテストしています。

**和暦は除外せず、換算して照合した（R009）**

「令和8年」の `8` も同じ理由で拾われていました。単に無視することもできましたが、換算して照合する形にしています。

令和8年3月期 → "March 2026"  … 指摘なし

令和8年3月期 → "March 2025"  … 要確認「2026（和暦 8 年からの換算）が訳文で確認できません」

無視していれば、この変換誤りは素通りしていました。同じ文に「令和8年」と「8拠点」があっても、後者は西暦に読み替えません（位置で判定）。

**断定表現に文脈を持たせた（R006）**

「確実に実施しました」（実績）まで要修正にすると、レポート全体が読まれなくなります。将来見通しを示す語（見込・予想・計画など）と同じ文にある場合だけ要修正へ上げています。

## 構成

```
src/ir_review/
├─ models.py     ドメインモデル。LLM の出力も必ずここの型に落としてから先へ進む
├─ textutil.py   正規化・数値抽出。表記差と実際の差を切り分ける
├─ glossary.py   用語集の読み込みと突合（LLM 不使用）
├─ rules.py      決定論的な検査ルール ★ 設計の中心
├─ ports.py      翻訳・レビューの境界（Protocol）
├─ llm.py        Claude API アダプタ。ここだけが Anthropic SDK を知る
├─ pipeline.py   オーケストレーション。処理の順番そのものが設計判断
├─ extract.py    PDF / テキストの読み込みとセグメント分割
├─ report.py     Markdown / JSON 出力
├─ jobs.py       非同期ジョブ管理（Web 用）
├─ ratelimit.py  レート制限（Web 用）
├─ api.py        HTTP API
├─ web.py        Web UI（単一ページ・外部CDN 非依存）
├─ cli.py        CLI
└─ config.py     設定と .env 読み込み
```

翻訳とレビューは `ports.py` の Protocol で切ってあります。これにより、

- テストはAPIキーなしで全件実行できる（フェイクを注入する）
- LLM の提供元を変えてもパイプラインは変わらない
- LLM を呼ばずに決定論的検査だけ回す運用ができる

が同時に成り立ちます。

### 処理の流れ

```
1. 抽出        文書 → Segment 列
2. 原文の検査  LLM 不使用。ここで取れる指摘はLLM に投げない
3. 翻訳        用語集をプロンプトに注入して英訳
4. 訳文の検算  用語集が守られたか、数値が一致するかをコードで確認
5. 再翻訳      4で違反が出たセグメントだけ、違反内容を添えて再依頼（上限あり）
6. LLM レビュー 2と4で取れないもの（文意・訳抜け・トーン）だけを見る
```

`translator` を渡さなければ 3〜6 は丸ごと省略され、APIキーなしで 1〜2 が動きます。

## 使い方

### セットアップ

```bash
python -m venv .venv
source .venv/bin/activate        # Windows: .\.venv\Scripts\Activate.ps1
pip install -e ".[dev,llm,api]"
pytest
```

### CLI

```bash
# 決定論的な検査のみ（APIキー不要・高速・無料）
ir-review review data/sample_disclosure_ja.md --no-translate

# 英訳とLLM レビューまで
ir-review review data/sample_disclosure_ja.md --translate --markdown report.md

# 試し実行（セグメント数を絞ってコストを抑える）
ir-review review path/to/disclosure.pdf --translate --max-segments 3

# 検査ルールの一覧
ir-review rules
```

要修正が残ると終了コード 1 を返すので、CIに組み込めます。

### Web UI

```bash
ir-review serve
# http://127.0.0.1:8000
```

### APIキー

`.env` に置くか、環境変数で渡します。`.env` は `.gitignore` 済みです。

```
ANTHROPIC_API_KEY=sk-ant-...
```

環境変数が既にある場合はそちらが優先されます（ホスティング側の設定を `.env` が黙って壊さないため）。

### 用語集

`data/glossary.sample.yaml` を編集するか、`--glossary` で差し替えます。

```yaml
- ja: 経常利益
  en: ordinary income
  aliases: [経常益]                              # 原文での揺れ表記
  forbidden_en: [recurring profit, pre-tax profit]  # 使用禁止の訳語
  note: 日本基準固有の科目のため、IFRSの語に置き換えないこと
```

## 設定

| 環境変数 | 既定 | 内容 |
| --- | --- | --- |
| `ANTHROPIC_API_KEY` | （なし） | 未設定なら決定論的検査のみ動作 |
| `IR_REVIEW_MODEL` | `claude-sonnet-4-5` | 使用モデル |
| `IR_REVIEW_MAX_PAGES` | `5` | PDFの読み込みページ数上限 |
| `IR_REVIEW_MAX_SEGMENTS` | `60` | 処理セグメント数の上限（＝LLM 呼び出し回数の上限） |
| `IR_REVIEW_MAX_TRANSLATE_RETRIES` | `1` | 用語集違反時の再翻訳回数 |
| `IR_REVIEW_ACCESS_KEY` | （空） | Web公開時のアクセスキー。空なら認証なし |
| `IR_REVIEW_RATE_LIMIT_PER_HOUR` | `10` | IP単位の時間あたり上限。0で無制限 |

上限値はコストと実行時間の事故を止めるためにあり、既定を保守的に置いています。

## Web 公開時の防御

公開を前提に、入口で止めるべきものを最初から実装しています。

- アクセスキー（`X-Access-Key`。`secrets.compare_digest` で比較。結果取得のエンドポイントにも同じ認証）
- レート制限（キーは共有されうるので、認証とは別に回数でも頭打ちにする）
- 同時実行数の上限（並列に走るとAPIコストと実行時間が読めなくなる）
- アップロード制限（8MB ・拡張子の許可リスト。書きながらサイズを数えて途中で止める）
- アップロードファイルは処理後に必ず削除（預かったものを残さない）
- ページ数・セグメント数の上限

長い処理はHTTP リクエストの中で待ちません。受付でジョブIDを返し、進捗を問い合わせてもらう形にしています。同期で待つと、ブラウザやプロキシのタイムアウトで「処理は走っているのに結果が受け取れない」という失敗になるためです。

ジョブはインメモリで持っています。デモと単一プロセス運用が前提で、再起動で消えることは許容します（消えたら再実行すればよく、失われて困る状態を持たない設計です）。複数インスタンスに増やす場合は、この層をRedis等に差し替えます。

## 開発

```bash
pytest              # テスト
ruff check .        # Lint
ruff format .       # フォーマット
mypy                # 型チェック（strict）
```

テストはAPIキーもネットワークも不要で全件実行できます。LLM はすべてフェイクに差し替えているためです。

回帰テストとして残している主なもの:

- SDK のバージョン差（`temperature` 非対応）で文書1本が丸ごと落ちないこと
- 空の環境変数が `.env` の読み込みを黙って阻害しないこと
- 英語の語で書かれた数値（月名・序数）を訳抜けと誤判定しないこと
- 用語集の禁止訳語を、語境界を見ずに部分一致させないこと
- 1セグメントの失敗で全体を止めないこと
